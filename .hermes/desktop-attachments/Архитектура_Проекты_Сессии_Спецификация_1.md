# Спецификация: иерархическая файловая структура «Раздел → Проект → Сессия» с БД-слоем

## Назначение документа

Это технический промт/ТЗ для внедрения в оболочку (приложение/агентскую среду) структуры хранения данных, при которой:
- каждый **Раздел** — физическая папка на диске, объединяющая проекты по смыслу;
- каждый **Проект** — физическая папка внутри раздела, содержащая всё, что к нему относится (сессии, файлы, промты, артефакты);
- каждая **Сессия** — либо привязана к проекту (хранится внутри его папки), либо является «свободной» (без проекта) и хранится в общей папке несвязанных сессий;
- вся иерархия зеркалируется в БД для быстрого поиска, связей и метаданных, при этом **источник истины по содержимому — файловая система**, а БД — индекс/кэш поверх неё, что обеспечивает переносимость на другую машину/оболочку простым копированием корневой папки.

---

## 1. Физическая структура файловой системы

```
/Workspace/                                  ← корень всего хранилища (можно перенести целиком)
│
├── _Sections/                               ← все разделы
│   ├── {section_id}__{section-slug}/        ← раздел = папка
│   │   ├── section.meta.json                ← метаданные раздела (имя, описание, дата создания, цвет/иконка)
│   │   │
│   │   ├── {project_id}__{project-slug}/    ← проект = папка внутри раздела
│   │   │   ├── project.meta.json            ← метаданные проекта
│   │   │   ├── sessions/                    ← все сессии, привязанные к этому проекту
│   │   │   │   ├── {session_id}__{date}/
│   │   │   │   │   ├── session.meta.json
│   │   │   │   │   ├── prompts/             ← история промтов сессии
│   │   │   │   │   ├── files/               ← файлы, созданные/загруженные в сессии
│   │   │   │   │   ├── attachments/         ← вложения пользователя
│   │   │   │   │   └── transcript.md        ← полный лог диалога
│   │   │   │   └── ...
│   │   │   ├── shared_files/                ← общие файлы проекта (не привязаны к конкретной сессии)
│   │   │   ├── prompts_library/             ← сохранённые/переиспользуемые промты проекта
│   │   │   └── exports/                     ← готовые выгрузки/результаты
│   │   │
│   │   └── ... другие проекты раздела
│   └── ... другие разделы
│
└── _Unassigned_Sessions/                    ← общая папка для сессий БЕЗ привязки к проекту
    ├── {session_id}__{date}/
    │   ├── session.meta.json
    │   ├── prompts/
    │   ├── files/
    │   └── transcript.md
    └── ...
```

### Правила именования
- `{id}` — короткий уникальный идентификатор (например, ULID/UUID7 — сортируется по времени создания, что удобно для папок).
- `{slug}` — человекочитаемое имя (транслит/латиница, без пробелов), чтобы папки были читаемы в любой ОС и облаке.
- Формат `{id}__{slug}` гарантирует уникальность даже при совпадении названий и удобство чтения глазами.

### Принцип переносимости
Вся информация о проекте — **без исключений** (промты, файлы любого типа, логи сессий, метаданные) — лежит физически внутри папки проекта. Это значит:
- Скопировал папку `/Workspace/` (или один раздел, или один проект) → перенёс на другой компьютер/оболочку → подключил БД (она пересоберётся сканированием) → всё работает.
- Никаких данных «только в БД» быть не должно — БД хранит только индекс и связи, не уникальный контент.

## 2. Слой базы данных

### Выбор СУБД
Рекомендация — **не MySQL**, а **SQLite** в качестве основной БД, по следующим причинам:
- SQLite — это тоже просто файл (`workspace.db`), который можно положить в корень `/Workspace/` и переносить вместе с папками — это соответствует требованию «всё в одной папке, легко переносимо».
- MySQL — это сервер, требующий отдельной установки/запуска на новой машине, что ломает идею «скопировал и работает».
- Если в будущем понадобится многопользовательский доступ/синхронизация через сеть — тогда есть смысл рассмотреть PostgreSQL как промежуточный слой синхронизации, но локальным источником истины всё равно остаётся файловая система + SQLite-индекс.

Итог: **SQLite-файл хранится по пути `/Workspace/_index/workspace.db`** и индексирует то, что есть на диске.

### Схема таблиц (SQLite)

```sql
-- Разделы
CREATE TABLE sections (
    id              TEXT PRIMARY KEY,        -- ULID
    slug            TEXT NOT NULL,
    name            TEXT NOT NULL,
    description     TEXT,
    path            TEXT NOT NULL,           -- относительный путь от корня /Workspace/
    color           TEXT,
    icon            TEXT,
    created_at      TEXT NOT NULL,
    updated_at      TEXT NOT NULL
);

-- Проекты
CREATE TABLE projects (
    id              TEXT PRIMARY KEY,
    section_id      TEXT NOT NULL REFERENCES sections(id) ON DELETE CASCADE,
    slug            TEXT NOT NULL,
    name            TEXT NOT NULL,
    description     TEXT,
    path            TEXT NOT NULL,
    status          TEXT DEFAULT 'active',   -- active / archived / paused
    tags            TEXT,                    -- JSON-массив тегов
    created_at      TEXT NOT NULL,
    updated_at      TEXT NOT NULL
);

-- Сессии (и привязанные, и свободные)
CREATE TABLE sessions (
    id              TEXT PRIMARY KEY,
    project_id      TEXT REFERENCES projects(id) ON DELETE SET NULL,  -- NULL = несвязанная сессия
    title           TEXT,
    path            TEXT NOT NULL,
    is_assigned     INTEGER NOT NULL DEFAULT 0,  -- 0 = в _Unassigned_Sessions, 1 = в проекте
    summary         TEXT,                        -- краткое авто-резюме сессии
    created_at      TEXT NOT NULL,
    updated_at      TEXT NOT NULL,
    last_opened_at  TEXT
);

-- Файлы (индекс файлов внутри проектов/сессий для быстрого поиска)
CREATE TABLE files (
    id              TEXT PRIMARY KEY,
    project_id      TEXT REFERENCES projects(id) ON DELETE CASCADE,
    session_id      TEXT REFERENCES sessions(id) ON DELETE CASCADE,
    path            TEXT NOT NULL,
    file_type       TEXT,                    -- pdf / docx / image / code / etc
    size_bytes      INTEGER,
    created_at      TEXT NOT NULL
);

-- Промты (переиспользуемая библиотека промтов на уровне проекта)
CREATE TABLE prompts_library (
    id              TEXT PRIMARY KEY,
    project_id      TEXT REFERENCES projects(id) ON DELETE CASCADE,
    title           TEXT,
    content         TEXT NOT NULL,
    created_at      TEXT NOT NULL
);

-- Индексы
CREATE INDEX idx_projects_section ON projects(section_id);
CREATE INDEX idx_sessions_project ON sessions(project_id);
CREATE INDEX idx_files_project ON files(project_id);
CREATE INDEX idx_files_session ON files(session_id);
```

### Принцип синхронизации диск ↔ БД
- При запуске оболочки — фоновый «сканер», который проверяет соответствие БД и реальной файловой структуры (на случай ручного переноса/правки папок вне приложения) и перестраивает индекс при расхождениях.
- Любая операция создания/переименования/удаления сначала выполняется на файловой системе, затем фиксируется в БД (порядок важен — ФС первична).

## 3. Логика поведения интерфейса (UX-флоу)

### 3.1 Создание раздела
1. Пользователь нажимает «Новый раздел».
2. Вводит название → система создаёт папку `/Workspace/_Sections/{id}__{slug}/` и файл `section.meta.json`.
3. Запись добавляется в таблицу `sections`.

### 3.2 Создание проекта
1. Пользователь выбирает раздел (или создаёт новый прямо тут же).
2. Вводит название проекта → создаётся:
   - папка `/Workspace/_Sections/{section}/{id}__{slug}/`
   - подпапки `sessions/`, `shared_files/`, `prompts_library/`, `exports/`
   - файл `project.meta.json`
3. Запись добавляется в таблицу `projects`.

### 3.3 Создание сессии (ключевой момент по ТЗ)
1. Пользователь нажимает «Новая сессия».
2. **Обязательно показывается модальное окно выбора:**
   - «Привязать к проекту» → выпадающий список (раздел → проект, с поиском/фильтром);
   - «Без проекта (отдельная сессия)» — кнопка по умолчанию доступна сразу.
3. В зависимости от выбора:
   - Если привязана → папка создаётся в `/Workspace/_Sections/{section}/{project}/sessions/{session_id}__{date}/`.
   - Если не привязана → папка создаётся в `/Workspace/_Unassigned_Sessions/{session_id}__{date}/`.
4. Запись добавляется в `sessions` с соответствующим `project_id` (NULL для свободной) и `is_assigned`.

### 3.4 Перепривязка сессии (дополнительная полезная функция)
Имеет смысл добавить возможность позже «приклеить» свободную сессию к проекту:
- Действие физически **перемещает** папку сессии из `_Unassigned_Sessions/` в `sessions/` нужного проекта.
- Обновляется `project_id` и `is_assigned` в БД, путь `path` пересчитывается.

## 4. Управление папками и файлами через интерфейс

Это слой UI поверх структуры из разделов 1–3: возможность кликнуть на Раздел/Проект/Сессию и получить полноценную панель управления — открыть физическую папку в системе, посмотреть, что внутри, добавить файлы, увидеть, какие инструменты к ней подключены.

### 4.1 Карточка объекта → Детальная панель (Detail Panel)

При клике на карточку Раздела, Проекта или Сессии открывается панель с вкладками:

| Вкладка | Содержимое |
|---|---|
| **Обзор** | название, описание, статус, теги, даты создания/изменения, кнопка «Открыть в файловом менеджере» |
| **Файлы** | дерево файлов этой папки (рекурсивно), кнопка «Добавить файл», превью по клику |
| **Сессии** (только у Раздела/Проекта) | список вложенных сессий с переходом внутрь |
| **Хуки и плагины** | какие инструменты подключены к этому объекту — см. раздел 5 |
| **Настройки** | переименовать, переместить в другой раздел/проект, архивировать, экспортировать, удалить |

Таким образом «нажав на следующую [папку]» пользователь видит именно то, что просил: с чем она работает (вкладка «Хуки и плагины») и что внутри (вкладка «Файлы»).

### 4.2 Открытие физической папки в системе («показать на диске»)

Кнопка «Открыть в Finder/Explorer» должна вызывать нативный файловый менеджер ОС с выделенной нужной папкой:

- **macOS:** `open -R "{abs_path}"` — открывает Finder и выделяет файл/папку;
- **Windows:** `explorer /select,"{abs_path}"`;
- **Linux:** `xdg-open "{abs_path}"` (выделение конкретного элемента зависит от DE, не везде поддерживается).

Важный архитектурный момент: если оболочка — desktop-приложение (Electron/Tauri), это делается напрямую через системный API (`shell.showItemInFolder()` в Electron). Если оболочка — веб-интерфейс в браузере, браузер **не может** по соображениям безопасности открыть локальный Finder/Explorer сам. В этом случае нужен небольшой локальный компаньон-процесс (фоновый helper/daemon на компьютере пользователя), который слушает локальный порт (например `http://127.0.0.1:PORT/reveal`) и по запросу от веб-интерфейса выполняет нужную команду ОС. Это нужно прямо сейчас заложить в архитектуру, если оболочка веб-based.

### 4.3 Просмотр структуры файлов внутри папки (File Tree)

- Компонент дерева файлов строится на основе таблицы `files` (уже описанной в разделе 2) — не сканирует диск при каждом клике, а читает индекс, что быстро даже для больших проектов.
- Поддиректории разворачиваются «лениво» (lazy load) — данные по вложенным файлам подгружаются только при раскрытии узла.
- У каждого файла отображается: иконка по типу (pdf/docx/image/code/...), размер, дата изменения.
- Превью по клику: для текстовых/markdown/изображений — показ содержимого прямо в панели, для остальных — кнопка «Открыть» (через тот же механизм reveal-in-OS).
- **File watcher** — фоновый процесс слежения за изменениями на диске (например, `chokidar` для Node.js, `watchdog` для Python, `fsnotify` для Go). Нужен, чтобы если пользователь добавил/удалил файл вручную через Finder, минуя интерфейс, — индекс в БД обновился автоматически, а не разошёлся с реальностью.

### 4.4 Добавление файлов в папку

- Кнопка «Добавить файл» в любой Detail Panel → системный диалог выбора файла → файл **копируется** в соответствующую физическую подпапку:
  - для Проекта → `shared_files/`;
  - для Сессии → `files/` (если создан внутри работы) или `attachments/` (если загружен пользователем);
- Поддержка drag-and-drop прямо в область дерева файлов.
- После копирования — запись добавляется в таблицу `files` (без ожидания следующего скана от file watcher, чтобы UI обновился мгновенно).

## 5. Система хуков и плагинов для сессий (инструменты/автоматизации)

Это отдельный расширяемый слой: возможность подключать к Сессии (а также к Проекту и Разделу — для каскадного применения) автоматические действия и ручные инструменты, не переписывая ядро системы каждый раз, когда нужна новая возможность.

### 5.1 Термины

- **Плагин (Plugin)** — переиспользуемый модуль-инструмент с определённой функцией: автосуммаризация сессии, экспорт в PDF/DOCX, отправка вебхука во внешнюю систему, git-синхронизация, запуск произвольного скрипта, интеграция с внешним API и т.п. Плагин существует один раз в системе и может быть подключён к множеству объектов.
- **Хук (Hook)** — конкретное подключение плагина к конкретному объекту (Разделу/Проекту/Сессии) с привязкой к событию жизненного цикла. Один плагин может быть подключён как хук в десятках разных мест с разными настройками.

### 5.2 События жизненного цикла, на которые можно подвешивать хуки

- `on_section_created`, `on_project_created`, `on_session_created`
- `on_session_closed`, `on_project_archived`
- `on_file_added`, `on_file_removed`
- `on_message_sent` — опционально, для лёгких автоматизаций на каждое сообщение (например, логирование, авто-тегирование по содержимому)
- `on_project_exported`

### 5.3 Структура плагина на диске

```
/Workspace/_plugins/{plugin_id}__{slug}/
├── plugin.manifest.json     ← название, версия, тип, поддерживаемые события, схема настроек
├── entrypoint.(js|py|sh)     ← точка входа (только для type = script)
└── icon.png
```

Пример `plugin.manifest.json`:
```json
{
  "id": "auto-summary-01",
  "name": "Auto-Summary",
  "version": "1.0.0",
  "type": "script",
  "supported_events": ["on_session_closed"],
  "config_schema": { "language": "string", "max_length": "number" },
  "entrypoint": "entrypoint.js"
}
```

### 5.4 Типы плагинов

| Тип | Как работает |
|---|---|
| `script` | Локальный исполняемый файл, запускается в отдельном процессе; получает JSON-контекст события (project_id, session_id, пути к папкам) через stdin/аргументы; может читать/писать файлы внутри папки объекта |
| `webhook` | HTTP POST на указанный URL с JSON-payload контекста — для внешних интеграций (свой сервер, Zapier/Make и т.п.) |
| `builtin` | Встроенная в саму оболочку функция, не требует внешнего кода — самые безопасные и быстрые из доступных вариантов |

Стартовый набор `builtin`-плагинов, которые стоит реализовать «из коробки»: Auto-Summary (авторезюме сессии в `session.meta.json`), Export to PDF/DOCX, Archive to ZIP, Webhook Notifier, Auto-Tag (по содержимому промтов).

### 5.5 Хранение в БД (дополнение к схеме из раздела 2)

```sql
-- Каталог доступных плагинов
CREATE TABLE plugins (
    id                  TEXT PRIMARY KEY,
    slug                TEXT NOT NULL,
    name                TEXT NOT NULL,
    description         TEXT,
    version             TEXT,
    type                TEXT NOT NULL,        -- script / webhook / builtin
    manifest_path       TEXT,
    supported_events    TEXT,                 -- JSON-массив событий
    created_at          TEXT NOT NULL
);

-- Подключения плагина к конкретному объекту (Раздел/Проект/Сессия)
CREATE TABLE hooks (
    id              TEXT PRIMARY KEY,
    plugin_id       TEXT NOT NULL REFERENCES plugins(id) ON DELETE CASCADE,
    scope_type      TEXT NOT NULL,            -- section / project / session
    scope_id        TEXT NOT NULL,            -- id раздела/проекта/сессии
    event           TEXT NOT NULL,            -- on_session_created и т.п.
    config          TEXT,                     -- JSON-настройки конкретного подключения
    inherit         INTEGER NOT NULL DEFAULT 0,  -- 1 = каскадно применяется ко всем дочерним объектам
    enabled         INTEGER NOT NULL DEFAULT 1,
    created_at      TEXT NOT NULL
);

-- Журнал запусков хуков (для отладки и истории)
CREATE TABLE hook_runs (
    id              TEXT PRIMARY KEY,
    hook_id         TEXT NOT NULL REFERENCES hooks(id) ON DELETE CASCADE,
    triggered_at    TEXT NOT NULL,
    status          TEXT,                     -- success / error / running
    log             TEXT
);

CREATE INDEX idx_hooks_scope ON hooks(scope_type, scope_id);
CREATE INDEX idx_hook_runs_hook ON hook_runs(hook_id);
```

Поле `inherit` решает задачу «подвесить хук на весь Раздел» — например, включить Auto-Summary сразу для всех новых сессий внутри раздела, а не настраивать каждую сессию вручную.

### 5.6 UI для хуков/плагинов

- Вкладка «Хуки и плагины» в Detail Panel показывает уже подключённые хуки текущего объекта (и те, что унаследованы от родительского Раздела/Проекта — с пометкой «унаследовано»).
- Кнопка «Подключить плагин» → каталог доступных плагинов из `/Workspace/_plugins/` → выбор события-триггера → форма настроек по `config_schema` → сохранение.
- Кнопка «Запустить инструмент вручную» — прямо из сессии можно вызвать подключённый плагин без ожидания события (полезно для экспорта, суммаризации «по требованию»).
- Лог последних запусков (из `hook_runs`) с результатом — успех/ошибка, чтобы было видно, что инструмент действительно сработал.

### 5.7 Безопасность

Так как `script`- и `webhook`-плагины выполняют внешний код или отправляют данные наружу, обязательны:
- запуск `script`-плагинов в изолированном процессе с минимальными правами (без доступа к остальной файловой системе, кроме папки объекта, к которому подключён хук);
- явное подтверждение пользователя при первом подключении плагина (по аналогии с разрешениями для расширений браузера);
- `builtin`-плагины считаются доверенными по умолчанию, `script`/`webhook` — всегда требуют ручного согласия.

## 6. Дополнительные рекомендации (от себя, по итогам анализа задачи)

1. **Файл `*.meta.json` в каждой папке** — это не обязаловка ради БД, а страховка: если БД потеряется/повредится, по этим файлам можно полностью восстановить индекс простым обходом дерева папок (rebuild from disk).

2. **Версионирование/бэкап** — стоит сразу заложить в `project.meta.json` поле `schema_version`, чтобы при будущих изменениях структуры можно было писать миграции, а не ломать старые проекты.

3. **Архивация** — для проектов со статусом `archived` имеет смысл не удалять папку, а просто визуально скрывать в интерфейсе (плюс можно физически архивировать в `.zip`, оставив в БД ссылку на путь к архиву вместо живой папки — экономит место при переносе на другую машину).

4. **Глобальный поиск** — раз все промты и файлы индексируются в SQLite (`files`, `prompts_library`), полнотекстовый поиск стоит делать через SQLite FTS5-таблицу — это бесплатно встроено в SQLite и не требует внешних сервисов.

5. **Лимит вложенности** — стоит явно зафиксировать, что глубина «Раздел → Проект → Сессия» строго трёхуровневая (без подразделов внутри разделов), иначе со временем структура усложнится и парсинг путей станет хрупким.

6. **Конфликты имён** — при создании двух проектов с одинаковым названием в одном разделе — система должна автоматически добавлять суффикс к `slug` (`-2`, `-3`...), при этом `id` всё равно гарантирует уникальность на уровне БД и пути.

7. **Перенос между оболочками** — раз ключевое требование — переносимость, стоит сразу предусмотреть команду «Экспортировать проект» = архивирование папки проекта целиком + `project.meta.json`, и «Импортировать проект» = распаковка + автоматическая регистрация в БД новой оболочки (с генерацией нового `id`, если такой уже существует, чтобы избежать коллизий).

8. **multi-device/облако (опционально на будущее)** — если впоследствии понадобится синхронизация между несколькими компьютерами (не просто разовый перенос), тогда стоит рассмотреть PostgreSQL + объектное хранилище (S3-совместимое) для файлов, но это отдельная архитектура — пока для одиночной локальной оболочки SQLite полностью покрывает задачу.

9. **Веб vs Desktop — критическая развилка для раздела 4.** Если оболочка реализуется как desktop-приложение (Electron/Tauri), пункты «открыть в Finder/Explorer» и file watcher делаются напрямую через системные API. Если оболочка веб-based — необходим локальный компаньон-процесс на машине пользователя; это нужно решить на самом раннем этапе проектирования, так как сильно влияет на архитектуру (нельзя добавить «потом» без существенной переделки).

10. **Идемпотентность хуков.** Плагин может не сработать из-за сбоя (нет сети для webhook, скрипт упал) — нужен механизм повторных попыток (retry) с экспоненциальной задержкой и явный статус `error` в `hook_runs`, чтобы пользователь видел, что автоматизация не выполнилась, а не считал, что всё прошло успешно.

11. **Разделение «каталога плагинов» и «установленных хуков».** Плагин из `/Workspace/_plugins/` — это просто доступный в системе инструмент (как приложение в App Store), а хук — это его подключение к конкретному объекту с конкретными настройками. Это разделение позволяет одному плагину обновляться один раз и сразу применяться везде, где он подключён, без необходимости переустанавливать его в каждом проекте отдельно.

## 7. Итоговый промт для агента-разработчика (краткая версия для вставки в систему)

```
Реализуй в оболочке трёхуровневую иерархию хранения: Раздел → Проект → Сессия.

1. Физически на диске:
   /Workspace/_Sections/{section_id}__{slug}/{project_id}__{slug}/sessions/{session_id}__{date}/
   /Workspace/_Unassigned_Sessions/{session_id}__{date}/ — для сессий без проекта

2. Каждый Раздел, Проект, Сессия — реальная папка с файлом *.meta.json внутри.
   Все данные сессии (промты, файлы, вложения, транскрипт) хранятся
   ТОЛЬКО внутри её папки — никаких данных только в БД.

3. При создании Раздела — создаётся папка раздела.
   При создании Проекта — создаётся папка проекта внутри выбранного раздела,
   с подпапками sessions/, shared_files/, prompts_library/, exports/.
   При создании Сессии — ОБЯЗАТЕЛЬНО показывать модальное окно выбора:
     [Привязать к проекту: <выбор раздела → проекта>] / [Без проекта]
   и в зависимости от выбора создавать папку сессии в соответствующем месте.

4. Параллельно вести индекс в SQLite-файле /Workspace/_index/workspace.db
   по схеме: sections, projects, sessions, files, prompts_library —
   с внешними ключами project_id/section_id/session_id.
   БД — это индекс/кэш, источник истины — файловая система.
   При расхождении — пересобирать БД сканированием диска.

5. Вся структура должна быть переносима: копирование папки /Workspace/
   (целиком или частично — один раздел/проект) на другую машину/оболочку
   и пересборка индекса должны полностью восстанавливать рабочее состояние.

6. Реализуй Detail Panel для Раздела/Проекта/Сессии с вкладками:
   Обзор / Файлы / Сессии / Хуки и плагины / Настройки.
   - Кнопка «Открыть в файловом менеджере» — выделяет физическую папку
     в Finder (macOS: open -R) / Explorer (Windows: explorer /select,)
     / файловом менеджере Linux (xdg-open). Если оболочка веб-based —
     реализуй локальный компаньон-процесс для выполнения этой команды.
   - Вкладка «Файлы» — дерево файлов из таблицы files (lazy load
     поддиректорий), с file watcher для авто-синхронизации изменений,
     сделанных вручную мимо интерфейса.
   - Кнопка «Добавить файл» — копирует файл в shared_files/ (проект)
     или files/ / attachments/ (сессия), с поддержкой drag-and-drop.

7. Реализуй систему плагинов и хуков:
   - Каталог плагинов в /Workspace/_plugins/{id}__{slug}/ с manifest.json
     (type: script / webhook / builtin, supported_events, config_schema).
   - Таблицы plugins, hooks, hook_runs в БД (схема — раздел 5.5).
   - Хук = подключение плагина к объекту (Раздел/Проект/Сессия) на событие
     жизненного цикла (on_session_created, on_session_closed,
     on_file_added и т.д.), с опциональным каскадным наследованием
     (поле inherit) на дочерние объекты.
   - UI: вкладка «Хуки и плагины» в Detail Panel — список подключённых,
     кнопка «Подключить плагин», кнопка ручного запуска инструмента,
     лог запусков с статусом success/error.
   - script/webhook-плагины требуют явного согласия пользователя при
     подключении и запускаются в изолированном процессе с ограниченными
     правами; builtin-плагины доверенные по умолчанию.
```
